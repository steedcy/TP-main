## DEF-S3-089：强行放行返回 500，拦截事件和审计丢失

关联 `TC-040.S2`、`TC-041.S3`、`SRS_F013.R07`，级别高。

1. 受控模型分别返回缺少 `precondition` 和包含 `while(true)` 的候选，实际生成任务 118、119。
2. 两任务自主版本均为结构 FAIL、能力 PASS、约束 PASS；原因分别为 `ERR_STEP_FIELD_MISSING`、`ERR_STEP_LOOP_DETECTED`，`frozenAt=null`，无匹配基线后进入 `PENDING_MANUAL`。
3. 对每个任务分别 POST `/api/v1/tasks/{id}/manual-actions`，动作 `FORCE_RELEASE` 和 `REQUEST_SUPERVISION`，附虚构处置原因。
4. 四次请求全部得到 **HTTP 500 / code 1000**，预期应为硬性拒绝 **4110** 并持久保存拦截事件/审计。请求后再次通过 API 和 SQL 取证，均无 `FORCE_BYPASS_INTERCEPTED` 事件或 `FORCE_BYPASS_ATTEMPT` 审计。
5. 两任务仍为 `PENDING_MANUAL`，未进入监督，步骤分配与设备指令均为 0。安全隔离子断言满足，但错误响应与必须留痕的要求失败，整步判 F。

数据库实际 `chk_op_log_result` 只允许 `SUCCESS`、`FAILED`、`CANCELLED`。产品 `TaskService.manualAction` 写入 `INTERCEPTED`，真实 PostgreSQL 拒绝该值，抛出约束异常，整个事务回滚。因此当前执行甚至没有到达预期的 `BusinessException(4110)`。

另有静态风险需修复方一并处理：该方法标注 `@Transactional`，`BusinessException` 是运行时异常；即使只放开数据库约束，随后抛出的 4110 仍可能导致同一事务中的拦截事件与审计回滚。此后半段是代码分析，**没有通过修改数据库约束来验证**。请在真实事务和迁移环境中验证拒绝响应及两种记录均持久化，不能只用 mock 的调用次数证明落库。
